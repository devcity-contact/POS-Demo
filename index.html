03 / System architecture

Modular monolith with Clean Architecture

Deploy one Spring Boot application initially, but enforce business-module boundaries. This keeps operations simple while allowing modules to evolve independently.

Recommended

Conceptual deployment view. Modules share one application process and database initially, but should own their domain logic and expose explicit application interfaces.

Why a modular monolith?

  • Simple deployment and lower infrastructure cost.
  • Database transactions for sales and stock.
  • Clear module boundaries for maintainability.
  • Extract a module into a service only when scale or team ownership requires it.

Clean Architecture inside each module

  • Domain: entities, value objects and business rules.
  • Application: use cases, commands, queries and ports.
  • Infrastructure: JPA, repositories and external adapters.
  • Presentation: REST controllers and request/response DTOs.

Data integrity: Keep a stock movement ledger and update the stock balance in the same database transaction. Use database constraints and locking to prevent overselling. A balance is a fast current-state projection; the movement ledger explains how it got there.

07 / Core workflows

End-to-end business operations

These flows define what “working MVP” means. Each critical operation should be transactional, auditable and idempotent where retries are possible.

Goods receiving creates batches

1
Create purchase order

Select supplier, variants, ordered quantities and expected cost.

2
Receive goods

Record actual received quantities; allow partial receiving.

3
Capture batch details

Batch number, expiry, purchase cost and optional selling price.

4
Post receipt

Create batches, stock movements and update balances atomically.

Checkout and batch allocation

Transaction boundary: Save sale, sale items, payment records, stock deductions, batch allocations and outbox event in one database transaction. External payment provider calls are not part of a database transaction; use payment states, idempotency keys and reconciliation for uncertain outcomes.

Returns, refunds and exchanges

Customer return

Reference the original sale item, returned quantity and original batch allocation where traceable. Inspect condition before restocking.

Refund

Record the refund as a separate financial transaction linked to the original payment/sale. Preserve the original sale.

Exchange

Model as a linked return plus a replacement sale. Collect or refund the price difference explicitly.

08 / Stock & batch design

Batch-aware stock and price handling

A product variant may have many batches. Each batch can have its own expiry and purchase cost, plus an optional selling-price override.

BatchExpiryAvailablePurchase costBatch selling price
B00130 Jan 2027100Rs. 80Rs. 100
B00215 Aug 2027150Rs. 90Rs. 120
B00310 Feb 2028200Rs. 95Use default price

Price resolution

  1. Resolve the active price list for the branch/customer.
  2. If the allocated batch has a valid selling-price override, use it.
  3. Otherwise use the applicable product variant price.
  4. Apply authorized discounts and tax rules.
  5. Snapshot the final price and cost on the sale allocation.

FEFO allocation

First Expiry, First Out is a good default for expiry-tracked stock.

  • Exclude expired, blocked or quarantined batches.
  • Sort eligible batches by expiry date.
  • Allocate until the requested quantity is fulfilled.
  • Allow manual batch choice only under configured policy and permissions.
Important: If one sale line is fulfilled from two batches at different prices, keep one logical sale item and create two sale-item allocation records. For example: 2 × Rs. 100 + 3 × Rs. 120 = Rs. 560. Preserve each allocation's batch, quantity, price and cost snapshot.

Stock visibility

The database is authoritative. Push updates are notifications to refresh views, not the mechanism that guarantees stock correctness. Use row locking or carefully designed optimistic concurrency for competing sales.

11 / Production readiness

What makes it production-ready?

Production readiness is not just architecture. It means protecting money, inventory, tenant data and operational continuity.

Data integrity

  • Money stored as DECIMAL / NUMERIC, never float.
  • Database transactions for sale + stock.
  • Idempotency for retried writes.
  • Immutable financial and stock history.

Security

  • Tenant isolation on every query and command.
  • RBAC and branch-level access.
  • Secure password hashing and token handling.
  • No raw card number or CVV storage.

Operations

  • Automated backups and restore drills.
  • Structured logs, metrics and traces.
  • Health checks and alerting.
  • Deployment rollback and migration plan.

Concurrency

  • Lock or version stock balances.
  • Prevent overselling.
  • Unique receipt / request identifiers.
  • Reconcile payment uncertainty.

Testing

  • Domain unit tests.
  • PostgreSQL integration tests.
  • Multi-tenant isolation tests.
  • Concurrent sale and refund tests.

Compliance

  • Use a compliant payment provider.
  • Assess PCI DSS obligations.
  • Respect local tax and invoice rules.
  • Define retention and privacy policies.
Scope warning — offline mode: Do not promise offline sales in the first release unless you design and test local transaction storage, device identity, idempotent sync, price validity and stock conflict policies. Offline card payments require explicit payment-provider support.
